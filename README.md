# AI-E1-2
개발자용 작업실 구축 과제 설명 및 수행 과정 보고서
1. 과제의 전체 목적
이번 과제는 단순히 프로그램 하나를 실행하는 것이 아니라, 개발자가 실제로 작업할 수 있는 기본 환경을 직접 구성하고 그 과정을 문서화하는 데 목적이 있다. 과제의 핵심은 내 컴퓨터에 개발 작업을 할 수 있는 “작업실”을 만들고, 그 작업실이 제대로 동작하는지 터미널 명령과 실행 결과를 통해 증명하는 것이다.

이 과제를 완료하면 학습자는 터미널 기반 작업, 파일 경로 이해, 파일 권한 이해, Docker를 이용한 컨테이너 실행, Dockerfile을 이용한 커스텀 이미지 제작, 포트 매핑, Docker 볼륨을 통한 데이터 영속성, Git과 GitHub를 이용한 버전 관리 및 원격 저장소 제출 과정을 설명할 수 있어야 한다.

즉, 이번 과제는 다음과 같은 흐름으로 진행된다.

내 개발 환경 확인
터미널에서 기본 명령어 수행
절대 경로와 상대 경로 이해
파일 권한 확인 및 설명
Docker 설치 및 동작 확인
Dockerfile 작성
웹 서버 컨테이너 빌드 및 실행
포트 매핑으로 브라우저 접속 확인
바인드 마운트와 볼륨을 통해 데이터 반영 및 유지 확인
Git 설정 및 GitHub 저장소 생성
README 문서 작성
GitHub Repository 링크 제출
이 과정에서 중요한 점은 “했다”라고 말하는 것이 아니라, 명령어 입력과 출력 결과를 함께 남겨 증명하는 것이다. 따라서 README 문서에는 각 단계에서 사용한 명령어, 실행 결과, 캡처 또는 로그, 문제 발생 시 해결 과정이 포함되어야 한다.

2. 최종 제출물의 구성
최종 제출물은 GitHub Repository 링크이다. 평가자는 해당 저장소 링크에 접속해서 과제 수행 결과 전체를 확인할 수 있어야 한다. 따라서 저장소 안에는 최소한 다음과 같은 자료가 포함되어야 한다.

첫째, README.md 파일이 필요하다. README는 이 과제의 중심 문서이다. README에는 프로젝트 개요, 실행 환경, 수행 항목 체크리스트, 검증 방법, 트러블슈팅, 실행 로그, 캡처 자료 링크 등이 들어가야 한다.

둘째, Dockerfile이 필요하다. Dockerfile은 기존 이미지를 바탕으로 나만의 커스텀 이미지를 만드는 설정 파일이다. 이 과제에서는 Dockerfile을 직접 작성해야 하므로, 단순히 기존 이미지를 실행만 해서는 부족하다.

셋째, 웹 서버 소스코드가 필요하다. 예를 들어 app/ 또는 src/ 폴더를 만들고 그 안에 간단한 웹 페이지나 서버 실행 파일을 둘 수 있다. 어떤 언어나 프레임워크를 사용하는지는 과제 조건에 따라 달라질 수 있지만, 핵심은 Dockerfile을 통해 웹 서버 컨테이너가 실행되고 브라우저에서 접속 가능해야 한다는 점이다.

넷째, Docker 실행 및 검증 로그가 필요하다. 예를 들어 Docker 버전 확인, Docker 정보 확인, 이미지 목록 확인, 컨테이너 목록 확인, 컨테이너 로그 확인, 컨테이너 상태 확인 등의 결과를 남겨야 한다.

다섯째, 포트 매핑 접속 증거가 필요하다. 컨테이너 내부에서 실행되는 웹 서버는 기본적으로 내 컴퓨터의 브라우저에서 바로 접근할 수 없다. 따라서 호스트 포트와 컨테이너 포트를 연결해야 하며, 브라우저 주소창에 포트가 포함된 주소와 응답 화면이 함께 보이도록 증거를 남겨야 한다.

여섯째, 바인드 마운트와 Docker 볼륨 증거가 필요하다. 바인드 마운트는 호스트 컴퓨터의 특정 폴더를 컨테이너 내부에 연결해서, 호스트에서 파일을 수정했을 때 컨테이너에도 반영되는지 확인하는 방식이다. Docker 볼륨은 컨테이너를 삭제하더라도 데이터가 유지되는지 확인하는 방식이다.

마지막으로 Git과 GitHub 연동 증거가 필요하다. Git 사용자 정보와 기본 브랜치 설정, GitHub 저장소 생성, VSCode와 GitHub 연동 등의 과정을 문서화해야 한다. 이때 토큰, 비밀번호, 개인 이메일 등 민감정보가 화면에 노출되지 않도록 주의해야 한다.

3. 개발 환경 확인
과제의 첫 단계는 현재 내 컴퓨터의 개발 환경을 확인하는 것이다. README에는 운영체제, 사용하는 쉘, 터미널 종류, Docker 버전, Git 버전 등을 정리해야 한다.

예를 들어 다음과 같은 항목을 문서에 작성할 수 있다.

운영체제: Windows / macOS / Linux 중 본인 환경
사용 터미널: PowerShell, Windows Terminal, macOS Terminal, iTerm2 등
사용 쉘: bash, zsh, PowerShell 등
Docker 버전
Git 버전
VSCode 사용 여부
이 정보를 적는 이유는 평가자가 README만 보고 동일한 절차를 재현할 수 있도록 하기 위해서이다. 개발 환경은 사람마다 다르기 때문에, 특정 개인 PC에만 적용되는 경로나 설정이 있다면 반드시 주의사항을 함께 적어야 한다.

예를 들어 절대 경로를 사용할 때 /Users/name/project 또는 C:\Users\name\project처럼 개인 이름이 포함될 수 있다. 이런 경우 README에는 “본인 환경에서는 해당 경로를 사용했으며, 다른 환경에서는 프로젝트 위치에 맞게 수정해야 한다”는 설명을 추가하는 것이 좋다.

4. 절대 경로와 상대 경로 설명
이번 과제에서 설명해야 할 중요한 개념 중 하나는 절대 경로와 상대 경로이다.

절대 경로는 파일 시스템의 최상위 위치부터 시작해서 특정 파일이나 폴더까지 가는 전체 경로를 의미한다. 예를 들어 macOS나 Linux에서는 /home/user/project 같은 형태가 절대 경로이고, Windows에서는 C:\Users\user\project 같은 형태가 절대 경로이다. 절대 경로는 현재 내가 어느 폴더에 있든 항상 같은 위치를 가리킨다.

반면 상대 경로는 현재 위치를 기준으로 파일이나 폴더를 찾는 방식이다. 예를 들어 현재 폴더 안에 app 폴더가 있다면 ./app이라고 표현할 수 있다. 상위 폴더로 이동해야 할 때는 ../를 사용할 수 있다. 상대 경로는 현재 터미널이 위치한 디렉터리에 따라 의미가 달라질 수 있다.

이번 과제에서는 Dockerfile, 소스코드, README, 로그 파일 등을 다루기 때문에 경로 개념이 중요하다. 특히 Dockerfile에서 파일을 복사하거나, Docker 실행 시 바인드 마운트를 설정할 때 경로를 정확히 이해해야 한다. README에는 본인이 사용한 경로가 절대 경로인지 상대 경로인지, 그리고 왜 그렇게 사용했는지를 간단히 설명하면 좋다.

5. 파일 권한 이해
파일 권한도 이번 과제의 주요 학습 목표 중 하나이다. 파일 권한에서 r, w, x는 각각 읽기, 쓰기, 실행 권한을 의미한다.

r: read, 파일을 읽을 수 있는 권한
w: write, 파일을 수정하거나 삭제할 수 있는 권한
x: execute, 파일을 실행하거나 디렉터리에 진입할 수 있는 권한
숫자로 표현되는 권한도 이해해야 한다. 예를 들어 755는 소유자, 그룹, 기타 사용자에게 부여된 권한을 숫자로 나타낸 것이다. 일반적으로 읽기 권한은 4, 쓰기 권한은 2, 실행 권한은 1로 계산한다.

예를 들어 7은 4+2+1이므로 읽기, 쓰기, 실행 권한이 모두 있다는 뜻이다. 5는 4+1이므로 읽기와 실행 권한이 있다는 뜻이고, 4는 읽기 권한만 있다는 뜻이다. 따라서 755는 소유자는 읽기, 쓰기, 실행이 가능하고 그룹과 기타 사용자는 읽기와 실행만 가능하다는 의미이다. 644는 소유자는 읽기와 쓰기가 가능하고, 그룹과 기타 사용자는 읽기만 가능하다는 의미이다.

README에는 파일 권한을 확인한 명령과 결과를 기록하고, 그 권한이 어떤 의미인지 설명해야 한다. 특히 실행 파일이나 스크립트를 다룬다면 실행 권한이 필요한 이유를 함께 적으면 좋다.

6. Docker 설치 및 기본 점검
Docker는 컨테이너 기반으로 프로그램 실행 환경을 격리하고 재현할 수 있게 해 주는 도구이다. 이번 과제에서는 Docker를 이용해 웹 서버 컨테이너를 만들고 실행해야 한다.

먼저 Docker가 설치되어 있고 정상 동작하는지 확인해야 한다. 이때 Docker 버전 확인, Docker 정보 확인 등의 명령을 실행하고 결과를 README에 기록한다.

중요한 점은 단순히 “Docker 설치 완료”라고 쓰는 것이 아니라, 실제 터미널에서 실행한 명령어와 출력 결과를 함께 남기는 것이다. 예를 들어 Docker 버전 확인 결과, Docker 데몬이 정상 실행 중인지 확인한 결과, 이미지 목록이나 컨테이너 목록을 확인한 결과 등을 기록해야 한다.

또한 Docker 관련 명령을 실행하다가 권한 문제나 데몬 실행 문제가 발생할 수 있다. 이런 문제가 발생하면 README의 트러블슈팅 항목에 문제, 원인 가설, 확인 방법, 해결 또는 대안을 순서대로 작성하면 된다.

7. Dockerfile 작성과 커스텀 이미지 생성
이번 과제에서는 Dockerfile을 직접 작성해야 한다. Dockerfile은 컨테이너 이미지를 만들기 위한 설계도라고 볼 수 있다. 기존 이미지를 기반으로 필요한 파일을 복사하고, 필요한 명령을 실행하고, 컨테이너가 시작될 때 어떤 동작을 할지 정의한다.

예를 들어 웹 서버를 실행하는 과제라면 Dockerfile 안에는 다음과 같은 역할이 들어간다.

어떤 기본 이미지를 사용할지 지정
작업 디렉터리 설정
웹 서버 소스코드 복사
필요한 의존성 설치
컨테이너에서 사용할 포트 명시
컨테이너 시작 시 실행할 명령 지정
Dockerfile을 작성한 뒤에는 이미지를 빌드해야 한다. 빌드 과정에서는 Dockerfile의 각 단계가 순서대로 실행된다. 만약 중간에 오류가 발생하면 어느 단계에서 실패했는지 로그를 보고 원인을 파악해야 한다.

빌드가 성공하면 이미지 목록에서 내가 만든 커스텀 이미지를 확인할 수 있다. README에는 Dockerfile 내용, 빌드 명령, 빌드 결과, 이미지 확인 결과를 함께 기록하는 것이 좋다.

8. 웹 서버 컨테이너 실행과 포트 매핑
Docker 컨테이너 안에서 웹 서버가 실행되더라도, 호스트 컴퓨터의 브라우저에서 바로 접근할 수 있는 것은 아니다. 컨테이너 내부의 포트와 내 컴퓨터의 포트를 연결해야 한다. 이것이 포트 매핑이다.

예를 들어 컨테이너 내부 웹 서버가 80번 포트에서 동작하고, 내 컴퓨터에서는 8080번 포트로 접속하고 싶다면 호스트 포트 8080과 컨테이너 포트 80을 연결한다. 이렇게 하면 브라우저에서 localhost:8080으로 접속했을 때 컨테이너 내부의 웹 서버 응답을 확인할 수 있다.

README에는 컨테이너 실행 명령, 포트 매핑 설정, 실행 결과, 브라우저 접속 화면을 기록해야 한다. 브라우저 증거를 남길 때는 주소창에 포트가 포함된 주소가 보여야 하고, 웹 서버 응답 화면도 함께 보여야 한다. 그래야 실제로 포트 매핑이 성공했음을 증명할 수 있다.

9. 바인드 마운트와 Docker 볼륨 검증
이번 과제에서는 바인드 마운트와 Docker 볼륨을 모두 다루어야 한다.

바인드 마운트는 호스트 컴퓨터의 특정 폴더를 컨테이너 내부 경로에 직접 연결하는 방식이다. 예를 들어 내 컴퓨터의 app 폴더를 컨테이너 안의 작업 디렉터리에 연결하면, 호스트에서 파일을 수정했을 때 컨테이너 내부에서도 변경 사항이 반영되는지 확인할 수 있다.

README에는 바인드 마운트 실행 명령, 변경 전 파일 내용, 호스트에서 수정한 내용, 변경 후 컨테이너 또는 브라우저에서 확인한 결과를 기록해야 한다. 핵심은 “호스트에서 바꾼 내용이 컨테이너 실행 결과에 반영되었다”는 점을 증명하는 것이다.

Docker 볼륨은 컨테이너가 삭제되어도 데이터를 유지하기 위한 방식이다. 일반적으로 컨테이너 내부에만 저장된 데이터는 컨테이너를 삭제하면 함께 사라질 수 있다. 하지만 볼륨을 사용하면 데이터가 Docker가 관리하는 별도 저장 공간에 남기 때문에 컨테이너를 삭제하고 다시 만들어도 데이터를 유지할 수 있다.

README에는 볼륨 생성, 컨테이너에 볼륨 연결, 데이터 생성 또는 변경, 컨테이너 삭제, 새 컨테이너 실행, 데이터 유지 확인 과정을 기록해야 한다. 여기서 중요한 것은 삭제 전과 삭제 후를 비교하는 증거이다.

10. Git과 GitHub 설정 및 제출
Git은 로컬에서 버전 관리를 하는 도구이고, GitHub는 원격 저장소를 제공하여 협업과 제출을 가능하게 하는 플랫폼이다. 이 둘은 비슷해 보이지만 역할이 다르다. Git은 내 컴퓨터 안에서 파일 변경 이력을 관리하고, GitHub는 그 변경 이력을 원격 서버에 올려 다른 사람이 확인할 수 있게 한다.

이번 과제에서는 Git 사용자 정보와 기본 브랜치 설정을 확인하고, GitHub Repository를 만들어 결과물을 업로드해야 한다. 또한 VSCode에서 GitHub 로그인을 하고 저장소와 연동한 증거도 필요하다.

다만 이 과정에서 개인 정보가 노출되지 않도록 주의해야 한다. 토큰, 비밀번호, 개인 이메일, 계정 정보 등이 로그나 이미지에 포함되면 안 된다. 만약 화면에 민감한 정보가 보이면 반드시 마스킹해야 한다.

최종 제출은 GitHub Repository 링크로 진행한다. 저장소 링크만으로 README, Dockerfile, 소스코드, 실행 로그, 검증 증거를 모두 확인할 수 있어야 한다.

11. README 작성 방법
README는 평가자가 가장 먼저 확인하는 문서이다. 따라서 단순히 명령어만 나열하는 것이 아니라, 전체 흐름을 이해할 수 있도록 구조화해야 한다.

추천 구성은 다음과 같다.

프로젝트 개요
실행 환경
수행 항목 체크리스트
절대 경로와 상대 경로 설명
파일 권한 설명
Docker 설치 및 점검 결과
Dockerfile 작성 내용
이미지 빌드 과정
컨테이너 실행 과정
포트 매핑 검증
바인드 마운트 검증
Docker 볼륨 영속성 검증
Git 및 GitHub 설정
트러블슈팅 2건 이상
최종 결과 확인 방법
특히 트러블슈팅은 최소 2건 이상 포함되어야 한다. 트러블슈팅은 단순히 “오류가 났고 해결했다”가 아니라, 다음 구조로 작성하는 것이 좋다.
